# Phase 4 Entity Resolution Audit

## 1. Existing Architecture
- **Candidate Generation**: Handled synchronously in `backend/app/ingestion/service.py` via Step 3a (spaCy/Regex) and Step 3b (LLM Semantic).
- **Resolution Engine**: `backend/app/nlp/resolution/engine.py` receives each candidate and attempts to resolve it against existing `CanonicalEntity` records in PostgreSQL.
- **Candidate Retrieval**: `find_candidates` (in `candidate_generation.py`) filters by entity type, using exact match for PHONE/VEHICLE, and a 3-character prefix search with `ilike` or alias membership for fuzzy matches.
- **Scoring**: `score_match` (in `matching.py`) utilizes `difflib.SequenceMatcher` to compute textual similarity between candidate and canonical names/aliases.
- **Persistence**: PostgreSQL is the source of truth (`canonical_entities` table). New canonicals and approved aliases are synchronized to Neo4j via `neo4j_intelligence`.

## 2. Current Capabilities
- **Fuzzy Name Matching**: String similarity via `difflib` for PERSON, ORGANIZATION, LOCATION.
- **Exact Matching**: Strict string equality for PHONE, VEHICLE.
- **Review Queue**: `api/v1/resolution.py` exposes a queue for `REVIEW_REQUIRED` candidates. Officers can `approve` or `create-entity`.
- **Normalization**: Basic lowercasing, spacing, and punctuation removal for names/locations. Extracts 10-digit formats for phones. Strips hyphens/spaces for vehicles.

## 3. Missing Capabilities (Gaps)
- **Multi-Signal Matching**: The system currently ONLY uses `name_similarity`. It does not compare phone numbers, vehicles, locations, or temporal data to strengthen or weaken a match for PERSON/ORGANIZATION entities.
- **False Merge Prevention (Conflict Detection)**: There is zero logic to prevent two identical names (e.g., "Ravi Kumar" and "Ravi Kumar") from automatically merging, even if one is a suspect in a 2026 FIR with Phone A, and the other is a victim in a 2010 FIR with Phone B.
- **Resolution Evidence Storage**: While a `resolution_score` is stored, the exact rationale (the "Why") is not persisted, preventing M1.12 Explainability from fully displaying the match logic.
- **Contextual Attribute Storage**: Phase 3 LLM extracts relationships and contextual data, but this context is not effectively populated into `CanonicalEntity.attributes` to aid future resolution.

## 4. Current Thresholds
- **PHONE / VEHICLE**: `1.0` (Exact Match) -> `AUTO_MATCHED`, else create new.
- **PERSON / ORG / LOC**: 
  - `1.0` -> `AUTO_MATCHED`
  - `>= 0.75` and `< 1.0` -> `REVIEW_REQUIRED`
  - `< 0.75` -> Create new `CanonicalEntity` (which gets `AUTO_MATCHED` to itself).

## 5. Current Data Model
- `EntityCandidate`: Stores `raw_text`, `normalized_value`, `entity_type`, `resolution_status`, `resolved_to_id`, `resolution_score`, and provenance (`ingestion_job_id`, `source_page`, `source_row`, `start_offset`, `end_offset`, `extraction_method`).
- `CanonicalEntity`: Stores `entity_type`, `name`, `aliases` (JSON array), and `attributes` (JSON dictionary for secondary signals like phone/location).

## 6. Current Limitations
- **O(N) Scanning Vulnerability**: The 3-character prefix `ilike` query in `candidate_generation.py` works for small datasets but will become a major bottleneck as the canonical entity table grows, especially for common names.
- **Silent Failures**: The code marks scores `< 0.75` as new canonical entities without flagging potential distant matches that might be valuable for intelligence.
- **Missing Linkage**: Relationships (like `REGISTERED_TO` or `COMMUNICATED_WITH`) are extracted *after* resolution, meaning the resolution engine cannot use them during the `resolve_candidate` pass.

## 7. Mock / Demo Behavior
- No hardcoded demo entities (like "Unknown Male") are created by the engine.
- However, the `score_match` function contains a TODO: `# TODO: Attribute overlap (e.g. check if they appear in same FIR, or share a phone)`. This reveals the system was left in a rudimentary M1.4 state.

## 8. Recommended Implementation Changes
1. **Weighted Match Score**: Redesign `score_match` to output a composite score: `Score = (Name * 0.5) + (Phone * 0.3) + (Vehicle * 0.2) + (Location * 0.1)`. (Weights configurable).
2. **Signal Aggregation**: Before resolving a candidate, pre-aggregate its context (e.g., look for phones extracted on the same page/row) so the resolution engine has secondary signals.
3. **Conflict Detection**: Introduce strict veto rules. If name similarity is 1.0 but phones explicitly mismatch, force `REVIEW_REQUIRED` or `Create New`.
4. **Resolution Evidence JSON**: Add a `resolution_evidence` JSON column to `EntityCandidate` to store the exact signal matches and weights used, powering the Explainability UI.
5. **Populate Canonical Attributes**: When merging or creating a CanonicalEntity, populate its `attributes` JSON with discovered phones, vehicles, and locations so future matches have data to compare against.
