# Phase 4: Entity Resolution Hardening — Architecture

## Overview

Phase 4 replaces the original single-signal (name-only) resolution engine with a multi-signal, context-aware system featuring explicit conflict detection and full evidence persistence.

## Architecture Flow

```
EntityCandidate (from Phase 3)
        ↓
ResolutionContext (built from same-page/row candidates)
        ↓
find_candidates()       ← Blocking keys: Name prefix, Exact Phone, Exact Vehicle
        ↓
score_match()           ← Weighted multi-signal scoring
        ↓
Decision Engine         ← Thresholds + Veto evaluation
        ↓
resolution_evidence     ← JSON persisted to entity_candidates.resolution_evidence
        ↓
CanonicalEntity         ← Attributes merged (phones, vehicles, locations)
        ↓
PostgreSQL              ← Source of truth
        ↓
Neo4j Sync              ← Graph projection layer
```

## ResolutionContext

A typed dataclass built before calling `resolve_candidate`. Context is scoped to candidates on the same **page** (PDF) or **row** (CSV/JSON).

```python
@dataclass
class ResolutionContext:
    phones: List[str]        # phones found alongside this candidate
    vehicles: List[str]      # vehicles found alongside
    locations: List[str]     # locations found alongside
    organizations: List[str] # orgs found alongside
    dates: List[str]         # dates found alongside
```

## Scoring Model

Weights are configured in `app/core/config.py` and default to:

| Signal      | Weight |
|-------------|--------|
| Name        | 0.50   |
| Phone       | 0.30   |
| Vehicle     | 0.15   |
| Location    | 0.05   |
| **Total**   | **1.00** |

**Formula:** `Score = (name_sim × 0.50) + (phone_match × 0.30) + (vehicle_match × 0.15) + (location_match × 0.05) − temporal_penalty`

Entity-type aware fast path applies to `PHONE`, `VEHICLE`, `ACCOUNT`: exact match required, no weighted scoring.

## Decision Thresholds

| Score Range           | Veto  | Decision         |
|-----------------------|-------|------------------|
| ≥ 0.80                | False | `AUTO_MATCHED`   |
| ≥ 0.65 and < 0.80    | False | `REVIEW_REQUIRED`|
| < 0.65                | False | `CREATE_NEW`     |
| Any                   | True  | `REVIEW_REQUIRED`|

## Veto Rules

Vetos represent strong explicit contradictions that override high name similarity:

- **Phone Mismatch**: Candidate has phone X, canonical has phone Y, no overlap → `veto=True`
- **Vehicle Mismatch**: Same logic for vehicle registrations → `veto=True`
- **Type Mismatch**: `PERSON` candidate vs `ORGANIZATION` canonical → `veto=True, REVIEW_REQUIRED`

> A veto **never** automatically creates a new entity. It always routes to human review.

## Temporal Evidence

Date differences are treated as a **penalty** (`−0.10`), not a hard veto. This is because FIR dates can be approximate or refer to different events in the same case. A temporal conflict alone never routes directly to `CREATE_NEW`.

## resolution_evidence JSON Structure

Every resolution decision persists its full rationale:

```json
{
  "score": 0.80,
  "decision": "AUTO_MATCHED",
  "veto": false,
  "signals": {
    "name_similarity": 1.0,
    "phone_match": 1.0,
    "vehicle_match": 0.0,
    "location_match": 0.0,
    "temporal_penalty": 0.0
  },
  "reason": "High confidence match."
}
```

This JSON is stored in `entity_candidates.resolution_evidence` and exposed via the `/api/v1/resolution/review-queue` API for M1.12 Explainability.

## Canonical Attribute Merging

When a candidate resolves to (or creates) a canonical entity, context signals are safely merged:

- Existing values are **never overwritten**
- New values are deduplicated before appending
- LLM-sourced attributes are stored as-is; they are not considered *confirmed* simply because an LLM produced them

## Candidate Retrieval (Blocking Keys)

`find_candidates` uses an OR-blocking strategy:

1. Name prefix (`ILIKE 'prefix%'`) — catches name variations
2. Exact phone in `attributes` JSON — strong blocking key for phone-linked persons
3. Exact vehicle in `attributes` JSON — strong blocking key for vehicle-linked persons

> **Limitation**: This is a heuristic blocking approach. A typo in a phone number will miss the phone blocking key and fall back to name prefix only.
