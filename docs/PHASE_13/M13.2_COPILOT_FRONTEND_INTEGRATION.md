# M13.2_COPILOT_FRONTEND_INTEGRATION

## 1. Objective
Connect the existing LINKRA Copilot frontend to the new `POST /api/v1/copilot/chat` architecture, replacing the legacy `POST /api/v1/chat/` dependency for the Copilot UI, without redesigning the interface or fabricating mock intelligence.

## 2. Before-state
- **Copilot UI** (`frontend/src/app/copilot/page.tsx`) was calling `chatService.sendMessage`.
- **`chat.service.ts`** was pointing to the legacy `POST /api/v1/chat/` endpoint.
- **Request schema** used `ChatRequest` (single `message` field).
- **Response schema** used `ChatResponse` (with `structured_data`, `record_count`, etc.).

## 3. Changes made
- Updated `chat.service.ts` to implement the `CopilotQuery` and `CopilotResponse` schemas.
- Modified `chatService.sendMessage` to point to `/copilot/chat`.
- Updated `page.tsx` mapping to correctly translate `CopilotResponse` fields (`answer`, `evidence`, `entities`, `sources`, `grounded`, `analytics`, `warnings`) into the local `Message` rendering state.
- Passed `xaiDetails` dynamically populated from the `sources` array instead of hardcoding to a system fallback message.

## 4. API migration
**IMPLEMENTED**
The Copilot frontend now communicates exclusively with the new `POST /api/v1/copilot/chat` architecture.

## 5. Request/response contract
**IMPLEMENTED**
- **Request:** Matches `CopilotQuery` (`message`, `investigation_id`, `entity_id`, `conversation_id`).
- **Response:** Matches `CopilotResponse` (`status`, `answer`, `intent`, `sources`, `evidence`, `entities`, `analytics`, `warnings`, `provider`, `grounded`).
- All schemas were enforced via TypeScript interfaces in `chat.service.ts`.

## 6. Authentication verification
**IMPLEMENTED**
The integration maintains the existing `apiClient.post` which automatically passes the JWT Bearer token on all requests to `/api/v1/*`. No authentication logic was bypassed or duplicated.

## 7. Legacy endpoint usage
**IMPLEMENTED**
- The frontend UI `frontend/src/app/copilot/page.tsx` has successfully been decoupled from `/api/v1/chat/`. 
- No other frontend components were using `chatService.ts`.
- The legacy backend endpoint `api/v1/chat.py` remains untouched in case external clients or other modules rely on it.

## 8. Real-data validation
**IMPLEMENTED**
- Verified that the UI uses only the data sent by the backend. No fabricated entities or mock graphs were added in the frontend.
- Fallbacks in UI handle empty sets for `entities` and `evidence`.

## 9. Error/empty/insufficient-data handling
**IMPLEMENTED**
- Handled HTTP errors and rate limits natively using the existing interceptors in `chat.service.ts`.
- Handled data states: Backend responds with `INSUFFICIENT_DATA` or similar status strings in `response.status`, which are exposed gracefully in the explainability panel (`reasoning: [Status: INSUFFICIENT_DATA, ...]`).
- Answers are rendered unmodified, ensuring the fallback mechanisms and empty-state responses defined on the backend are presented identically to the user.
