# M9.1 — Real Timestamped Data Audit

## 1. Database Audit
An inspection of the PostgreSQL schema (via SQLAlchemy models) reveals the following temporal fields:
- **`Crime`**: `occurrence_date` (DateTime), `reported_date` (DateTime). These represent genuine event and reporting times.
- **`EntityRelationship`**: `event_timestamp` (DateTime). This is nullable and represents the time an interaction/relationship occurred.
- **`Investigation`**: `started_at`, `completed_at` (DateTime). Administrative timestamps.
- **`Alert`**: `created_at`, `resolved_at` (DateTime). Administrative timestamps.
- **`Officer`**: `assigned_at` (DateTime). Administrative timestamp.
- **`EventAuditLog`**, **`Document`**, **`IngestionJob`**: System/administrative tracking timestamps.

## 2. Real Data Profiling
A live query of the PostgreSQL database yielded the following:
- **Crimes**: 1,000 records. All contain `occurrence_date` and `reported_date`. Range: 2024-09-03 to 2026-09-03.
- **Canonical Entities**: 50 records (Person: 16, Org: 11, Date: 10, Event: 9, Location: 2, Phone: 1, Vehicle: 1).
- **Relationships**: 16 total records in `entity_relationships`. 
- **Timestamped Events**: Only 8 relationships contain a valid `event_timestamp`. All 8 share a single timestamp (2023-01-15).
- **Conclusion**: The intelligence graph itself is extremely sparse. While crime reports exist, the structured entity/relationship graph contains virtually zero temporal variance.

## 3. Temporal Data Sufficiency
- **Temporal spike detection**: **NO**. We cannot establish historical activity or detect deviations with only 8 timestamped relationship events occurring on a single day.
- **Time-series baseline**: **NO**. A meaningful baseline requires longitudinal data over days/weeks/months. 
- **Statistical thresholds**: **NO**. There is insufficient historical variance to calculate defensible thresholds like mean or standard deviation.

## 4. Communication Anomaly Data
**Status: NOT DATA-SUPPORTED**
There is no `communications`, `phone_calls`, or `messages` table. The graph contains only 1 `PHONE` entity and generic relationship types (`CONNECTED_TO`, `ASSOCIATED_WITH`), none of which reflect genuine communication frequency or timing.

## 5. Transaction Anomaly Data
**Status: NOT DATA-SUPPORTED**
There is no `transactions` or `financials` table. There are no fields for `transaction_amount`, `sender`, or `receiver`.

## 6. Location Anomaly Data
**Status: NOT DATA-SUPPORTED**
There are only 2 `LOCATION` entities and no location-history tracking table to indicate movement patterns or frequency of visits over time.

## 7. Isolation Forest Feasibility
**Status: NOT JUSTIFIED**
An Isolation Forest requires a sufficiently large dataset of observations with diverse, meaningful numerical features to map out normality and isolate anomalies. Training on 50 entities or 16 relationships will trivially overfit or flag everything.

## 8. Existing Structural Anomaly Audit
- **Implementation Location**: `backend/app/ai/neo4j/anomaly.py`
- **API Endpoints**: `backend/app/api/v1/graph_anomalies.py` (`/top`, `/{entity_id}`)
- **Algorithm/Logic**: Detects `HIGH_DEGREE`, `ISOLATED_ENTITY`, and `RELATIONSHIP_CONCENTRATION` using native Neo4j Cypher queries based on node degrees and isolated subgraphs.
- **Data Reality**: Uses genuine graph data.
- **Limitations**: Cypher queries enforce a minimum entity requirement (currently returns "At least 5 entities are required" if insufficient subgraph volume exists).

## 9. Evidence & Provenance Readiness
**Status: READY**
The schema in `backend/app/schemas/graph.py` contains `AnomalyExplanation` and `AnomalySignal`. The system is architecturally ready to trace anomalies back to `evidence` nodes, fulfilling the "WHY" and "WHAT source" requirement without hallucinatory generation.

## 10. Frontend Audit
**Status: READY**
The frontend contains `AnomalyCard.tsx` (in `frontend/src/components/Intelligence/`), which currently visualizes structural anomalies and can easily be extended to display temporal anomalies if the underlying data existed. No UI overhaul is necessary.

## 11. Architectural Decision
### OPTION C: INSUFFICIENT DATA
The real dataset does not contain sufficient timestamped behavioral data. Phase 9 Behavioral and Temporal Anomaly Detection is officially **DEFERRED**. 

**Missing Requirements**:
- At least several hundred relationship edges with diverse `event_timestamp` values spanning multiple months.
- Specific interaction sub-tables (or typed relationships) with fields like `duration`, `amount`, or `coordinates` for communication, transaction, or location anomalies.
