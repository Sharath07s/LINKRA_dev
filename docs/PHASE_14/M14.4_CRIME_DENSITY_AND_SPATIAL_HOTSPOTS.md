# M14.4 — Crime Density and Spatial Hotspots

## 1. Objective

Transform verified real crime locations from the PostGIS `crimes` table into observed spatial crime density clusters, using a scientifically defensible algorithm (`ST_ClusterDBSCAN`). Visualize these density regions as map polygon overlays in the production MapLibre map, clearly distinguished from individual crime points and from any predictive intelligence.

## 2. Existing Spatial Data

- **Total crimes with valid geometry:** 1000
- **Unique coordinate count:** 1000
- **Coordinate system:** EPSG:4326 (WGS84), stored as `geometry(Point, 4326)`
- **Geographic extent:** Approximately Karnataka state (lat 11°–19°, lon 74°–79°)
- **Temporal coverage:** Multiple months of occurrence dates
- **Crime types:** Multiple categories (House Breaking, Cyber Fraud, Vehicle Theft, Larceny, etc.)
- **Districts:** Multiple districts represented

## 3. Spatial Method Selection

**Chosen method:** PostGIS `ST_ClusterDBSCAN`

### Why this method was chosen

1. **Data distribution:** 1000 unique coordinates spread across Karnataka. Grid-based density would force rigid cell boundaries that don't correspond to natural spatial clusters.
2. **DBSCAN properties:** Density-based clustering naturally discovers arbitrarily shaped concentration regions without requiring a predefined number of clusters.
3. **PostGIS native:** Runs entirely in PostgreSQL — no external computation, no data movement.
4. **Reproducibility:** Deterministic given the same parameters and data.

### Alternatives evaluated

- **Grid/Hex aggregation:** Considered but rejected. With 1000 points across a state-sized area, most grid cells contain 0–3 crimes. DBSCAN produces more meaningful clusters.
- **K-Means:** Rejected. Requires specifying k in advance, which is arbitrary for observed density analysis.
- **Client-side heatmap only:** Rejected as sole approach. A MapLibre heatmap is a visualization technique, not a spatial algorithm. The backend must compute the clusters.

## 4. Parameters

| Parameter | Value | Justification |
|-----------|-------|---------------|
| `eps` | 0.05 degrees | ~5.5km at Karnataka latitudes. Captures urban crime clusters without merging distant districts. |
| `minpoints` | 5 | A cluster must contain at least 5 crimes to be considered a meaningful spatial concentration. |

### Coordinate system note

PostGIS `ST_ClusterDBSCAN` with SRID 4326 uses degrees for `eps`. At Karnataka's latitude (~15°N), 0.05° longitude ≈ 5.4km and 0.05° latitude ≈ 5.6km. This is an approximation acceptable for observed density analysis at this scale.

## 5. Spatial Query Implementation

```sql
WITH clustered AS (
    SELECT location, ST_ClusterDBSCAN(location, eps := 0.05, minpoints := 5) OVER () AS cluster_id
    FROM crimes
    WHERE location IS NOT NULL
    [AND optional bbox/date filters]
),
cluster_hulls AS (
    SELECT 
        cluster_id, 
        COUNT(*) as crime_count,
        ST_ConvexHull(ST_Collect(location)) as geom
    FROM clustered
    WHERE cluster_id IS NOT NULL
    GROUP BY cluster_id
)
SELECT cluster_id, crime_count, ST_AsGeoJSON(geom) as geojson
FROM cluster_hulls
ORDER BY crime_count DESC
```

All filter parameters (bbox, start_date, end_date) are parameterized via SQLAlchemy `text()` bound parameters. No raw SQL concatenation.

## 6. Density Calculation

Each cluster's density is represented by:

- **`crime_count`**: The number of real crime records in the cluster.
- **`density_score`**: Set equal to `crime_count` (a simple, defensible metric).

No invented risk scores, severity indices, or composite formulas.

## 7. Hotspot Definition

A **hotspot** in M14.4 is defined as:

> A spatial cluster of ≥5 real crime records located within approximately 5.5km of each other, identified by the PostGIS `ST_ClusterDBSCAN` algorithm.

The geometry represents the **convex hull** of the clustered points — the smallest convex polygon enclosing all crimes in the cluster.

### What a hotspot is NOT:

- A district crime count
- A predictive forecast
- A risk assessment
- A subjective ranking

## 9. API

### `GET /api/v1/geo/crime-density`

**Authentication:** JWT required (same as existing geo endpoints)

**Parameters:**

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|

## 10. GeoJSON Response

```json
{
  "type": "FeatureCollection",
  "features": [
    {
      "type": "Feature",
      "geometry": {
        "type": "Polygon",
        "coordinates": [[[lon1, lat1], [lon2, lat2], ...]]
      },
      "properties": {
        "cluster_id": 12,
        "crime_count": 66,
        "density_score": 66.0
      }
    }
  ]
}
```

Non-polygon results (e.g., degenerate clusters where all points are collinear) are filtered out.

## 11. MapLibre Visualization

The production map (`/map`) now renders three layer types:

1. **Density polygons** (`fill` + `line` layers): Convex hulls of DBSCAN clusters, color-coded by `crime_count` from amber (low) to red (high).
2. **Crime points** (`circle` layer): Individual real crime locations (from M14.3).
3. **Interactive toggles**: Investigators can independently show/hide the density and point layers.

A density legend indicates the color scale and method.

## 16. Limitations

1. `eps=0.05` degrees is an approximation (~5.5km). At different latitudes, the actual distance varies.
2. Convex hulls may overestimate cluster boundaries if points are irregularly distributed.
3. No crime-type or district filtering is currently wired through the density endpoint (planned for M14.5).
4. No persistence layer — clusters are computed dynamically on each request.
5. Performance has not been validated at production scale (>100k crimes).
