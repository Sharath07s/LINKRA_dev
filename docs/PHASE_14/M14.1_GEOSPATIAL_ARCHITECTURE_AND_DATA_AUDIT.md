# LINKRA — PHASE 14 / M14.1
# GEOSPATIAL ARCHITECTURE AND DATA AUDIT

## 1. Objective and Architecture Validation

The objective of this audit is to determine the current state of geographic capabilities across the LINKRA architecture, specifically targeting PostgreSQL/PostGIS, backend geospatial APIs, and frontend MapLibre integrations.

**Architecture Adherence Confirmed:**
The existing architecture (PostgreSQL -> FastAPI -> Next.js/MapLibre) has been validated as the definitive flow. PostgreSQL remains the authoritative source for geographic data. Neo4j handles relationship intelligence but is *not* used as the geographic source of truth.

## 2. PostgreSQL & PostGIS State

A deep audit of the PostgreSQL database and SQLAlchemy models revealed the following:

*   **PostGIS Extension:** **NOT INSTALLED.** A query of `pg_extension` confirms PostGIS is absent from the database environment.
*   **Spatial Column Types:** The `latitude` and `longitude` columns on `crimes` and `police_stations` are standard `Numeric` types, not PostGIS `geometry` or `geography` types.
*   **Spatial Indexes:** There are **NONE** (no GiST indexes exist for bounding box or spatial proximity queries).
*   **Data Sufficiency:**
    *   **Crimes:** 1000/1000 records have both `latitude` and `longitude` populated.
    *   **Police Stations:** 100/100 records have coordinates populated.
    *   **Districts:** 20 verified districts exist (e.g., Kodagu, Belagavi, Tumakuru).

**Audit Finding:** The database contains sufficient raw coordinate data (100% coverage for crimes and stations), but lacks the fundamental spatial infrastructure (PostGIS and Geometry types) required for actual geospatial intelligence, radius searches, or spatial clustering.

**Status:** INFRASTRUCTURE-BLOCKED (Requires PostGIS installation and schema migration to `geometry(Point, 4326)` in a subsequent milestone).

## 3. Backend Spatial API Audit

An inspection of the backend API routes responsible for geospatial mapping and hotspots (`predictive`, `executive`, `command_wall`, `investigations`) revealed the following:

*   **`predictive/hotspots`**: Currently uses pseudo-spatial logic. It groups crimes temporally by `district_id` and calculates percentage acceleration rates as a proxy for "hotspots". It selects a single, arbitrary sample coordinate from the district to represent the hotspot. It does not perform actual density-based spatial clustering (like DBSCAN or PostGIS spatial joins).
*   **`executive/hotspots` & `command_wall/hotspots`**: These endpoints simply group by `District.name` and count crimes. They return a list of top districts (e.g., `[{"district": "Kodagu", "count": 63}]`) but do not return coordinates or GeoJSON.
*   **`investigations/{id}/locations`**: This endpoint successfully formats data into a GeoJSON `FeatureCollection`. However, it only returns a single `Point` feature corresponding to the primary crime of the investigation.

**Audit Finding:** The backend currently relies on basic SQL `GROUP BY district_id` operations rather than true spatial clustering.

**Status:** INFRASTRUCTURE-BLOCKED (Backend logic cannot perform spatial clustering without PostGIS or spatial Python libraries).

## 4. Frontend MapLibre Audit

The Next.js frontend has a mix of mock and functional map components. The core dependencies (`maplibre-gl` v5.24.0 and `react-map-gl` v8.1.1) are correctly installed in `package.json`.

*   **Mocked / CSS-Based Maps:**
    *   `MapContainer.tsx`: Renders an empty state ("Map Intelligence Unavailable").
    *   `LiveCrimeMap.tsx`: Renders a CSS radial-gradient background with a text warning ("MapLibre Integration Required for Geospatial Rendering").
    *   `CrimeHotspotsMap.tsx`: Uses abstract CSS blurred blobs (emerald, red, amber) to mimic a heatmap instead of using actual geospatial data.
    *   `CaseMapPanel.tsx`: Converts long/lat to CSS percentage values (`left: 50% + ...`) to overlay glowing dots on an abstract grid.

*   **Functional (But Hardcoded) MapLibre Implementations:**
    *   `app/map/page.tsx`: Contains a fully working MapLibre implementation utilizing `<Map>`, `<Source>`, `<Layer>` (for heatmaps), and `<Marker>` (for clusters).
    *   **The Catch:** The data driving this map is a hardcoded `HOTSPOTS` array containing 4 fake hotspots (e.g., "Indiranagar - Halasuru Sector", "Mysuru - Vidyaranyapuram").

**Audit Finding:** The frontend has the required libraries and one excellent structural implementation (`app/map/page.tsx`), but heavily relies on CSS mocks and hardcoded fake arrays across the dashboard and command wall components.

**Status:** DATA-BLOCKED (Frontend components are awaiting real GeoJSON API integrations from the backend).

## 5. Conclusion & Next Steps

This audit (M14.1) confirms that while the raw coordinate data exists (100% of crimes geocoded), the spatial infrastructure is entirely missing.

To achieve genuine geospatial intelligence in Phase 14, the following must happen in subsequent milestones:
1.  **Database Migration:** Enable PostGIS and convert numeric `latitude`/`longitude` to `geometry(Point, 4326)` with GiST indexes.
2.  **API Refactoring:** Refactor backend endpoints to execute PostGIS spatial queries (`ST_DWithin`, `ST_ClusterDBSCAN`) instead of district-level string grouping.
3.  **Frontend Integration:** Rip out CSS map mocks and the hardcoded `HOTSPOTS` array in `app/map/page.tsx`, replacing them with live API calls to the new PostGIS-backed endpoints.
