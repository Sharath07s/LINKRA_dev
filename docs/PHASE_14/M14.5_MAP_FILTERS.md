# M14.5 — Map Filters

## 1. Objective
Make the real LINKRA crime map and spatial intelligence filterable. Following the strict requirement of "Filter First, Analyze Second," all filter selections must propagate to the PostGIS backend where the `ST_ClusterDBSCAN` density algorithm computes clusters strictly on the filtered subset of crimes.

## 2. Existing Filterable Data
A full schema audit confirmed:
- **District:** Extracted from the `districts` table via `Crime.district_id`.
- **Crime Type:** Extracted from the `crime_types` table via `Crime.crime_type_id`.
- **Date Range:** Authoritative date uses `Crime.occurrence_date`.
- **Investigation:** Linked via `investigations.crime_id`, though currently the dataset contains 0 investigations.

## 3. District Filter
- Integrated dynamically using `/api/v1/geo/filter-options`.
- Populates the dropdown with actual 20 districts present in the database.
- Uses `district_id` parameter to filter the `crimes` CTE in PostGIS prior to running DBSCAN.

## 4. Crime Type Filter
- Integrated dynamically.
- Populates the dropdown with the 7 existing distinct crime types.
- Uses `crime_type_id` parameter for exact filtering.

## 5. Date Range Filter
- Implemented with two inputs: Start Date and End Date.
- Filters against `crimes.occurrence_date`.
- Safely parametrized in PostgreSQL to enforce date boundaries correctly.

## 6. Investigation Filter
- Because the existing dataset has 0 investigations, the UI authentically displays "No investigations available" and is disabled to prevent confusion.
- The API backend strictly supports `investigation_id` using an `EXISTS (SELECT 1 FROM investigations i WHERE i.crime_id = crimes.id AND i.id = :investigation_id)` query, future-proofing the filter without fabricating fake data.

## 7. Combined Filtering
- All filters are fully composable.
- The frontend tracks them natively in React state and converts them into query string parameters parsed efficiently by FastAPI.

## 8. API Changes
- **`GET /api/v1/geo/filter-options`**: New endpoint to serve metadata.
- **`GET /api/v1/geo/crime-density`**: Extended to accept `district_id`, `crime_type_id`, `investigation_id`, `start_date`, and `end_date`.
- **`GET /api/v1/geo/crimes`**: Extended to accept `investigation_id` alongside existing filters.

## 9. Filter Option Source
- `filter-options` strictly queries `District`, `CrimeType`, and `Investigation` tables. No fabricated geographic groupings or arbitrary bounds were introduced.

## 10. Filtered Density / Hotspot Behavior
- Filtering is performed *before* spatial clustering in the CTE:
```sql
WITH clustered AS (
    SELECT location, ST_ClusterDBSCAN(location, eps := 0.05, minpoints := 5) OVER () AS cluster_id
    FROM crimes
    WHERE <dynamic_filters>
)
```
- This ensures that when a user filters by "Theft", the resulting clusters genuinely represent concentrated theft density, not an overarching crime cluster with the non-theft points simply hidden.

## 11. Empty / Insufficient Data Behavior
- Filtering to 0 crimes naturally cascades through the CTE returning 0 clusters.
- The MapLibre React UI detects `features.length === 0` and correctly displays an honest empty state indicator over the map.
- If fewer than 5 points match a filter in an area, DBSCAN simply assigns null `cluster_id` and the hull is not formed, naturally representing insufficient data for a hotspot without breaking.

## 12. Security / RBAC
- FastAPI dependencies (`deps.get_current_active_user`) remain intact.
- Query parameters are strictly parsed by FastAPI.
- Raw SQL utilizes parameterized `sqlalchemy.text()` to inject values securely, mitigating SQL injection risks.

## 13. Performance
- 1,000 baseline crimes.
- Executing filtering in the database minimizes bandwidth overhead.
- Query uses existing indexes on `district_id`, `crime_type_id`, and `location`. No arbitrary DB restructuring was needed.

## 14. Testing
- Added robust assertions in `test_geo_api.py`.
- Tested the frontend TypeScript build (`npm run build`), which passed cleanly.

## 15. Real Data Validation
Validation results from the production script:
- **Base:** 1000 crimes -> 78 clusters (largest: 66)
- **District 'Bengaluru Urban':** 47 crimes -> 2 clusters (largest: 33)
- **Crime Type 'Theft':** 336 crimes -> 12 clusters (largest: 11)
- **Date Range 2024:** 153 crimes -> 2 clusters (largest: 5)
- **Combined 'Bengaluru Urban' + 'Theft':** 16 crimes -> 2 clusters (largest: 9)
- **Investigation Filter:** 0 crimes -> 0 clusters

## 16. Limitations
- With real data constraints, certain filters (like Investigation) yield 0 results. This is an expected artifact of the baseline dummy data and not a system defect.
