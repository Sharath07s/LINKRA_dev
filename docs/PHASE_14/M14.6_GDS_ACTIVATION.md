# M14.6: GDS Activation and AuraDB Free Tier Connectivity Fix

## Objective
Activate real graph community detection (Louvain and Leiden algorithms) on the LINKRA Neo4j database to support the Intelligence tier and Copilot.

## The Infrastructure Blocker
When initially attempting to run GDS procedures via the `graphdatascience` Python client, the following routing error occurred:
`UnableToConnectError: Unable to retrieve routing information`

### Root Cause
The `graphdatascience` client attempts to connect using the `neo4j+s://` protocol and tries to invoke dedicated GDS sessions using Aura API (`AuraApi`). However, **AuraDB Free tier instances do not support dedicated AuraDS (Data Science) session provisioning endpoints.**
The Free tier uses a self-signed certificate (requiring `neo4j+ssc://`) and has GDS procedures *embedded* directly in the core database engine, not in a separate compute node. 

## The Solution
We bypassed the `graphdatascience` wrapper library and used the standard `neo4j` Python driver to execute GDS Cypher procedures directly against the main database.

### Implementation Pattern
For AuraDB Free tier, GDS projections must define the `memory` inline. The correct sequence is:

1. **Drop existing projection (if any):**
   ```cypher
   CALL gds.graph.drop('linkra_community_graph', false)
   ```

2. **Project the graph with inline memory parameter:**
   ```cypher
   CALL gds.graph.project(
       'linkra_community_graph',
       '*',
       '*',
       {
           undirectedRelationshipTypes: ['*'],
           memory: '2GB'
       }
   )
   ```

3. **Execute the Algorithm (Louvain/Leiden):**
   ```cypher
   CALL gds.louvain.stream('linkra_community_graph')
   YIELD nodeId, communityId
   RETURN gds.util.asNode(nodeId).id AS entity_id,
          gds.util.asNode(nodeId).name AS name,
          labels(gds.util.asNode(nodeId))[0] AS type,
          communityId
   ORDER BY communityId, entity_id
   ```
- `algorithm`: allow-listed to `louvain` and `leiden`. Defaults to `louvain`.
- Reject invalid algorithms.

### 5. Final Validation Results

* **Independent GDS Execution**: 
  - Louvain successfully assigned 73/73 nodes into 70 distinct communities (68 singletons, 2 multi-member).
  - Leiden successfully assigned 73/73 nodes into 70 distinct communities (68 singletons, 2 multi-member).
* **Graph Integrity**: Confirmed 0 modifications to nodes or relationships (Graph size: 73 nodes, 16 relationships).
* **API Exposure**: Both Louvain and Leiden are fully exposed via the `/api/v1/graph/analytics/communities` REST API using the `algorithm` query parameter.
* **Copilot Integration**: `_tool_neo4j_community_lookup` passes real analytics to the LLM (using the default Louvain) without data fabrication.

### 6. Original Infrastructure Blocker History

The original Aura Graph Analytics session approach was blocked due to an `UnableToConnectError`. M14.6 was subsequently activated and independently validated through direct Neo4j-driver execution of the supported GDS procedures (`gds.louvain.stream` and `gds.leiden.stream`) against the real LINKRA database, preserving the fixed architecture. The algorithm correctly grouped tightly connected nodes (e.g., specific entities, locations, organizations, dates, and investigation tags) while isolating disconnected nodes into their own singleton communities.

## Integration
This logic has been integrated into `backend/app/ai/neo4j/community.py`, specifically replacing the `INFRASTRUCTURE_DEFERRED` mock response. The `Neo4jCommunityAnalytics` class now instantiates its own driver using application credentials (`app.core.config.settings`) and executes the inline Cypher operations on-demand. 
This data flows seamlessly into the `/api/v1/communities` endpoint and the Copilot `COMMUNITY_LOOKUP` tool, fully activating the Intelligence tier's community detection feature.
