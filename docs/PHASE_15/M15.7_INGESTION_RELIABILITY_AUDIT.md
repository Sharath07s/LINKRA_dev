# M15.7 — Ingestion Reliability, Dead-Letter & Recovery Audit

## Executive Summary
This document presents the Phase 0 Read-Only Audit of the LINKRA ingestion pipeline architecture, failure handling, transactional boundaries, partial-data footprint, and recovery capabilities. It establishes the baseline for building the M15.7 Reliability, Dead-Letter & Recovery layer.

---

## 1. Current Ingestion Architecture & Pipeline Audit

The ingestion pipeline (`backend/app/ingestion/service.py`) orchestrates document processing synchronously in the web request or background runner without external task queues.

### Pipeline Steps Overview
1. **Job Initialization (`Step 1`)**:
   - Inserts `IngestionJob` record with status `QUEUED`.
   - File saved under `uploads/<uuid>_<filename>`.
2. **Document Parsing (`Step 2`)**:
   - Updates status to `PROCESSING` (`started_at = utcnow`).
   - Dispatches to format parser (`parse_pdf`, `parse_csv`, `parse_json`, `parse_txt`).
   - Updates status to `PARSED` (`record_count` populated).
3. **Entity Extraction (`Step 3`)**:
   - spaCy NER + Regex rule extraction across document pages/rows.
   - LLM Extraction (`extract_entities_llm`) for `FIR` or `POLICE_REPORT` source types.
   - Deduplicates spaCy vs LLM candidates in-memory.
   - Updates status to `EXTRACTED`.
4. **Entity Resolution & Candidate Persistence (`Step 4`)**:
   - Iterates through `EntityCandidate` items.
   - Executes resolution engine (`resolve_candidate`), linking to `CanonicalEntity`.
   - Adds `EntityCandidate` instances to PostgreSQL session and commits (`db.commit()`).
5. **Relationship Extraction & Graph Sync (`Step 5`)**:
   - Extracts page-level relationships using spaCy/Regex or LLM rules.
   - Persists `EntityRelationship` in PostgreSQL (`db.commit()`).
   - Synchronizes entities & relationships to Neo4j graph database (`sync_canonical_entity`, `create_relationship`).
6. **RAG Vector Indexing & Document Chunking (`Step 6`)**:
   - Splits page text into sub-page chunks using `RecursiveCharacterTextSplitter`.
   - Embeds chunks using sentence-transformers (`all-MiniLM-L6-v2`) and persists `DocumentChunk` records with vector embeddings to pgvector via `VectorStore.index_document()`.
   - Runs evidence linking (`link_evidence_for_job`).
   - Updates final `IngestionJob` status (`COMPLETED`, `COMPLETED_PARTIAL`, or `FAILED`).

## 2. Ingestion State Machine Audit

### Current States in DB (`IngestionJob.status`)
- `QUEUED`: File uploaded, job record initialized.
- `PROCESSING`: Parsing initialized.
- `PARSED`: Document structure extracted.
- `EXTRACTED`: Entity candidates extracted.
- `COMPLETED`: Entire pipeline including vector indexing completed cleanly.
- `COMPLETED_PARTIAL`: Entity/relationship extraction succeeded, but some RAG vector chunks failed indexing.
- `FAILED`: Pipeline failed either during parsing/extraction or when 100% of vector chunks failed indexing.

### Gaps in State Machine
- No explicit `DEAD_LETTER` or `RETRYABLE_FAILURE` state.
- No distinction between transient failures (e.g. temporary DB connection/embedding service timeouts) and permanent failures (e.g. corrupt PDF, invalid schema).
- No retry tracking state machine (`retry_count`, `max_retry_count`, `failed_step`, `recovery_status`).

---

## 3. Failure Behavior & Error Storage Audit

### Exception Catching Locations
- **Step 6 Exception Block**: Catches vector/embedding errors isolated from main pipeline. Job status set to `FAILED` or `COMPLETED_PARTIAL`, keeping previously committed PostgreSQL entity candidates and relationships.
- **Top-Level `except Exception` Block**: Catches unhandled errors in Steps 1–5. Sets `job.status = "FAILED"`, `job.completed_at = datetime.now(timezone.utc)`, and `job.error_message = str(e)[:2000]`.

### Error Metadata Deficiencies
1. **No Failure Step Identification**: `failed_step` is not stored on `IngestionJob`. Investigators cannot tell at a glance if a job failed during PDF parsing, spaCy NER, LLM resolution, graph sync, or vector embedding.
2. **Truncated Raw Error Only**: Only the first 2,000 characters of `str(e)` are saved to `error_message`.
3. **No Stack Traces or Diagnostic Identifiers**: No structured error code (`error_code`), sanitized trace representation, or retry metadata (`last_retry_at`, `next_retry_at`, `retry_count`).
4. **Secret Safety**: Raw exception strings could theoretically leak filesystem paths or service keys if third-party libraries output credentials in exception text. Sanitization is missing.

## 4. Transaction Boundaries & Partial Data Footprint Audit

### Current Transaction Behavior
The pipeline executes **multiple separate commits** throughout execution:
- Commit 1: `IngestionJob` created (`QUEUED`).
- Commit 2: `status = PROCESSING`, `started_at` updated.
- Commit 3: `status = PARSED`, `record_count` updated.
- Commit 4: `status = EXTRACTED`.
- Commit 5: `EntityCandidate` records committed to PostgreSQL.
- Commit 6+: `EntityRelationship` records committed to PostgreSQL AND pushed to Neo4j.
- Commit 7+: `DocumentChunk` records committed to PostgreSQL + pgvector.

### Partial Data State on Failure
- If Step 5 (Relationship/Neo4j Sync) fails halfway:
  - `EntityCandidate` rows remain persisted in PostgreSQL.
  - Some `CanonicalEntity` rows may have been updated/created.
  - Partial `EntityRelationship` rows exist in PostgreSQL and partial nodes/edges exist in Neo4j.
- If Step 6 (RAG Vector Indexing) fails:
  - All candidates, canonical entities, relationships, and Neo4j nodes exist.
  - Partial or zero `DocumentChunk` rows exist in pgvector.

### Idempotency Assessment on Rerunning Jobs
Currently, there is **no retry API or rerun method**. If a job is manually rerun or re-processed:
- `EntityCandidate`: Will create duplicate `EntityCandidate` rows referencing the new or existing `ingestion_job_id` unless previously cleaned up.
- `CanonicalEntity`: Entity resolution matches candidates against existing `CanonicalEntity` rows or creates new ones. Multiple runs would accumulate candidates linked to canonical entities.
- `EntityRelationship`: `extract_relationships_for_page` does NOT check for pre-existing relationships for the same job, risking duplicate `EntityRelationship` rows.
- `DocumentChunk`: `VectorStore.index_document` does not delete existing chunks for an `ingestion_job_id` before re-indexing, resulting in duplicate chunks in `document_chunks`.
- `Neo4j Graph`: Neo4j uses `MERGE` queries for nodes and relationships (`MERGE (e:Entity {id: ...})`), making node/edge creation idempotent, though property updates overwrite previous states.

## 5. Security & RBAC Audit

### Current Ingestion RBAC
- Upload API `POST /api/v1/ingestion/upload` requires `RoleChecker(["OFFICER", "ADMIN", "SUPER_ADMIN"])`.
- List API `GET /api/v1/ingestion/` requires authenticated user (`get_current_active_user`).
- Get Detail `GET /api/v1/ingestion/{job_id}` requires authenticated user.

### Missing Recovery RBAC
- No retry API `POST /api/v1/ingestion/{job_id}/retry` exists yet.
- Authorization must ensure only authorized roles (`OFFICER`, `ADMIN`, `SUPER_ADMIN`) can trigger retries, and normal investigators cannot retry jobs without permission.

## 6. Frontend Ingestion UI Audit

- Path: `frontend/src/app/data-sources/page.tsx`
- Service: `frontend/src/services/ingestion.service.ts`
- Status Display: Displays job status badge (`COMPLETED`, `PROCESSING`, `FAILED`).
- Error Display: Shows `error_message` string if present.
- Missing Features: No retry button, no modal confirmation, no failure step display, no retry count indicator.

## 7. Reliability Gaps Summary

| Gap Area | Description | Required M15.7 Solution |
|---|---|---|
| **State Representation** | Binary `FAILED` status gives no recovery context. | Extend schema with retry metadata (`failed_step`, `error_code`, `retry_count`, `max_retry_count`, `recovery_status`). |
| **Error Persistability** | Stack traces & step details lost. | Bounded, secret-sanitized failure metadata recording. |
| **Idempotency** | Re-running job duplicates candidates, relationships & vector chunks. | Implement cleanup/idempotent overwrite strategy before reprocessing a job. |
| **Recovery Engine** | No backend API or retry logic exists. | Implement `POST /api/v1/ingestion/{job_id}/retry` with RBAC, state validation, and concurrency locks. |
| **Concurrency Lock** | Simultaneous retry requests could cause race conditions. | Use atomic status transition (`PROCESSING` lock) or database-level checks. |
| **Investigator UI** | No retry workflow or clear failure step visibility. | Add failure details, retry count, modal confirmation, and retry trigger in `data-sources/page.tsx`. |

---

## 8. Conclusion
The audit demonstrates that the LINKRA ingestion architecture is well-structured but lacks an idempotent recovery mechanism and failure state tracking. M15.7 will add a database-backed reliability and retry layer on top of `IngestionJob` while preserving all existing PostgreSQL, Neo4j, and RAG components.
