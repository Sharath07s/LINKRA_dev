# M15.7.1 — Durable Source Storage: Phase 0 Audit

**Date:** 2026-09-22  
**Branch:** main  
**Alembic Current:** `m157_recovery_fields` (head)

---

## 1. How the Uploaded Source File Is Currently Stored

The upload endpoint (`POST /api/v1/ingestion/upload`) saves the raw bytes to a local directory:

```
backend/uploads/{uuid.hex}_{original_filename}
```

- `UPLOAD_DIR = Path(__file__).resolve().parent.parent.parent / "uploads"`
- Directory is created with `mkdir(parents=True, exist_ok=True)`
- The safe filename uses a UUID prefix to prevent collisions but NOT path traversal
- **File is saved BEFORE the IngestionJob is created**
- Only `file_name` (the original filename without UUID prefix) is stored on `IngestionJob`

**Gap**: The UUID-prefixed real filesystem path is NOT recorded anywhere in the database. On retry, `retry_ingestion_job()` does a glob `UPLOAD_DIR.glob(f"*_{job.file_name}")` to find it, which is fragile if the uploads/ directory is wiped.

---

## 2. How IngestionJob References the Source

`IngestionJob.file_name` stores only the **original filename** (e.g., `test_fir.txt`), not the full path.

The UUID-prefixed disk path (e.g., `uploads/abc123_test_fir.txt`) is only known at upload time and is NOT persisted to the database.

There is **no durable source reference** — no storage key, no checksum, no provider field.

---

## 3. Where the Local Working File Is Located

```
backend/uploads/{uuid.hex}_{original_filename}
```

At retry time, the service does:
```python
matching_files = list(UPLOAD_DIR.glob(f"*_{job.file_name}"))
file_path = str(matching_files[0]) if matching_files else str(UPLOAD_DIR / job.file_name)
```

This glob can fail if:
- Multiple files match `*_{filename}` (ambiguous)
- The uploads/ directory was cleared
- The server was restarted on a different machine/container

---

## 4. When the Local File Is Deleted

**Never explicitly deleted** by the current code. Files accumulate in `uploads/` indefinitely until manually cleaned.  
However, in containerized/ephemeral environments (Docker restart, Heroku dyno cycle, etc.), the entire `uploads/` directory is lost.

## 9. How Retry Reconstructs the Source Path

Current (fragile) pattern in `retry_ingestion_job()`:
```python
matching_files = list(UPLOAD_DIR.glob(f"*_{job.file_name}"))
file_path = str(matching_files[0]) if matching_files else str(UPLOAD_DIR / job.file_name)

if not os.path.exists(file_path):
    # → PERMANENT_FAILURE: SOURCE_FILE_MISSING
```

**Problem**: If the local file exists, it proceeds. If not → permanent failure immediately, even if a durable copy could be restored.

**M15.7.1 fix**: Add `restore_source_for_job()` that fetches from durable storage, verifies SHA-256, and writes a local working copy.

---

## 10. Cleanup Order

Current order in `retry_ingestion_job()`:
1. Locate source file (glob)
2. Check file exists → fail if missing
3. Increment retry counter
4. `cleanup_job_outputs()` ← **destructive: deletes EntityCandidates, Relationships, Chunks**
5. `execute_pipeline()`

**M15.7.1 required order**:
1. Lock job
2. Validate retry eligibility
3. Locate / verify durable source
4. Restore local working copy
5. Verify SHA-256
6. **ONLY THEN** `cleanup_job_outputs()`
7. Re-run pipeline

This prevents: durable source check fails → cleanup has already destroyed partial outputs → job is now in worse state.

---

## 11. DocumentChunk Provenance

`DocumentChunk.metadata_json` stores:
- `ingestion_job_id`
- `source_filename` (the original filename, not the local path)
- `source_type`
- `file_type`
- `page_number`
- `chunk_index`

This provenance does NOT depend on local filesystem paths — it uses the logical filename. Safe for recovery.

---

## 12. M15.4 RAG Requirements

No changes needed to `VectorStore.index_document()` or `semantic_search()`. The embedding pipeline reads `page.text` from the parsed document, not from the local file path directly after parsing. As long as the local working copy is restored before `execute_pipeline()` is called, RAG works normally.

## Conclusion

The Phase 0 audit confirms:
- No existing durable storage — local `uploads/` only
- No Supabase Storage credentials available in environment
- Migration head is clean (`m157_recovery_fields`)
- Implementation will use `LocalPersistentStorageProvider` for development/testing
- Supabase Storage provider skeleton will be included but not activated unless credentials are provided
- Critical retry ordering bug must be fixed (source verification BEFORE cleanup)
