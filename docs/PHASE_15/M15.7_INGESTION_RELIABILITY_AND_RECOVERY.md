## Executive Summary
This document provides the technical specification and architectural walkthrough for **M15.7: Ingestion Reliability, Dead-Letter & Recovery**. It outlines how LINKRA handles failed document ingestion jobs, maintains PostgreSQL as the authoritative source of truth, performs secret-sanitized failure logging, ensures 100% idempotent output reprocessing, locks against concurrent retries, and provides investigator-facing failure diagnostics and recovery actions.

---

## 1. Existing Ingestion Lifecycle & Step Execution Model

The ingestion pipeline (`backend/app/ingestion/service.py`) operates as a synchronous pipeline:

```
IngestionJob (QUEUED)
      ↓
Step 2: PARSING (PROCESSING → PARSED)
      ↓
Step 3: ENTITY_EXTRACTION (spaCy NER + Regex + LLM)
      ↓
Step 4: ENTITY_RESOLUTION (Resolution Engine → CanonicalEntity)
      ↓
Step 5: RELATIONSHIP_EXTRACTION (EntityRelationship → PostgreSQL + Neo4j)
      ↓
Step 6: EMBEDDING_GENERATION / VECTOR_PERSISTENCE (DocumentChunk → pgvector)
      ↓
Step 7: EVIDENCE_LINKING (Grounding EntityRelationship → DocumentChunk)
      ↓
Final Status: COMPLETED | COMPLETED_PARTIAL | FAILED
```

---

## 2. Failure Model & Dead-Letter Representation

Failed ingestion jobs remain fully persistent and observable on the `ingestion_jobs` database table (which acts as the database-backed dead-letter repository).

### Failure States
- `FAILED`: Pipeline failed at a specific step.
- `COMPLETED_PARTIAL`: Entity/relationship extraction succeeded, but some RAG vector chunks failed indexing.
- `RECOVERY_STATUS`:
  - `NONE`: Default for newly created jobs or completed jobs.
  - `RETRYABLE`: Failure caused by transient network, timeout, or external service unavailability.
  - `PERMANENT_FAILURE`: Failure caused by corrupt documents, missing source files, or unsupported formats.
  - `EXHAUSTED`: Retries attempted `max_retry_count` times without success.
  - `RECOVERED`: Job was successfully retried and reached `COMPLETED`.

## 3. Failure Metadata Fields

The `IngestionJob` model (`backend/app/models/ingestion.py`) was extended via Alembic migration (`m157_ingestion_recovery_fields.py`) with:

| Field | Type | Description |
|---|---|---|
| `failed_step` | `String(100)` | Step where failure occurred (`PARSING`, `ENTITY_EXTRACTION`, `ENTITY_RESOLUTION`, `RELATIONSHIP_EXTRACTION`, `EMBEDDING_GENERATION`, `NEO4J_SYNC`, `EVIDENCE_LINKING`) |
| `error_code` | `String(100)` | Standardized diagnostic error code (`EMBEDDING_PROVIDER_UNAVAILABLE`, `NEO4J_UNAVAILABLE`, `PARSER_FAILURE`, `SOURCE_FILE_MISSING`, `UNSUPPORTED_OR_CORRUPT_DOCUMENT`, `UNEXPECTED_ERROR`) |
| `retry_count` | `Integer` | Number of retries attempted (default `0`) |
| `max_retry_count` | `Integer` | Bounded retry threshold (default `3`) |
| `last_retry_at` | `DateTime(TZ)` | Timestamp of last retry attempt |
| `failed_at` | `DateTime(TZ)` | Timestamp when job failed |
| `recovery_status` | `String(50)` | Recovery lifecycle state (`NONE`, `RETRYABLE`, `EXHAUSTED`, `PERMANENT_FAILURE`, `RECOVERED`) |

### Secret Sanitization
All exception strings passed to `job.error_message` pass through `sanitize_error_message()`, which strips JWT bearer tokens, database connection credentials (`postgres://...`), API keys, and filesystem passwords using regex rules.

## 4. Reprocessing & Idempotency Strategy

### Strategy Chosen: Safe Full Reprocessing with Idempotent Output Cleanup
- **Rationale**: Step-level resume introduces subtle corruption risks if entity IDs or document chunk indices changed midway. Performing a clean full reprocessing from the preserved source file with pre-execution output cleanup guarantees 100% data consistency across PostgreSQL, Neo4j, and pgvector.
- **Cleanup Sequence (`cleanup_job_outputs`)**:
  1. Delete `EvidenceLink` records referencing relationships or chunks belonging to `ingestion_job_id`.
  2. Delete `EntityRelationship` records for `ingestion_job_id`.
  3. Delete `EntityCandidate` records for `ingestion_job_id`.
  4. Delete `DocumentChunk` records for `ingestion_job_id` from PostgreSQL / pgvector (`VectorStore.delete_job_chunks`).
  5. Re-execute ingestion pipeline.
  6. Neo4j graph nodes & edges are updated using Cypher `MERGE` queries (`MERGE (n:Entity {id: ...})`), preventing graph duplicate nodes/edges.

## 5. Security & RBAC

- Endpoint: `POST /api/v1/ingestion/{job_id}/retry`
- Authentication: Mandatory Bearer JWT (`get_current_active_user`).
- Authorization: Mandatory `RoleChecker(["OFFICER", "ADMIN", "SUPER_ADMIN"])`. Unauthenticated calls yield `401 Unauthorized`; unauthorized roles yield `403 Forbidden`.

## 6. Concurrency Control

Simultaneous duplicate retries for the same job are prevented via **Atomic Database State Transitioning**:
```python
affected_rows = db.query(IngestionJob).filter(
    IngestionJob.id == job_id,
    IngestionJob.status.in_(["FAILED", "COMPLETED_PARTIAL"])
).update({"status": "PROCESSING"}, synchronize_session=False)
db.commit()

if affected_rows == 0:
    raise HTTPException(status_code=409, detail="Job is currently being retried or processed by another request.")
```
If two investigators click "Retry" at the exact same moment, the first query transitions `status` to `PROCESSING` atomically, causing the second query to affect 0 rows and return `409 Conflict`.
