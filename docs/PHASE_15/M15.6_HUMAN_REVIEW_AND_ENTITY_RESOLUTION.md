# M15.6 — Human Review and Entity Resolution

This document details the architecture and implementation of the missing Human-in-the-Loop Entity Resolution interface for LINKRA. This milestone enables investigators to resolve ambiguous entity candidates that the automated system flagged for review.

## 1. Existing Automatic Resolution Flow
During the document ingestion pipeline:
1. `EntityCandidate` records are created for each extracted entity mention.
2. The pipeline computes a `ResolutionContext` and invokes the matching engine.
3. Candidates that strongly match a known `CanonicalEntity` are marked `AUTO_MATCHED` and linked (`resolved_to_id`).
4. Candidates that fail to match any entity are assigned a `CREATE_NEW` decision, creating a new `CanonicalEntity` and linking them.
5. If the resolution encounters conflicting signals (e.g., mismatching phone numbers for the same name) or falls into a medium-confidence tier, the candidate is flagged as `REVIEW_REQUIRED`.

## 2. The `REVIEW_REQUIRED` State
Candidates in the `REVIEW_REQUIRED` state are left partially unlinked but contain an initial proposed canonical entity in their database record. The human review UI exposes these candidates so investigators can definitively resolve them.

## 3. Human Review Workflow
The investigator review queue (accessible via `/resolution`) queries the database for all `REVIEW_REQUIRED` candidates. For each candidate, the UI displays:
- The candidate's raw and normalized text.
- The document context (job, page, row).
- A dynamically generated list of top `possible_matches` (ranked by confidence).

## 4. Review Queue API
`GET /api/v1/resolution/review-queue`
- Fetches all `REVIEW_REQUIRED` candidates (paginated).
- Dynamically recalculates `ResolutionContext` using other entities extracted in the same scope to generate robust blocking keys.
- Computes `possible_matches` containing `canonical_entity_id`, `name`, and `match_score` for each candidate.

## 5. Confirm Action
`POST /api/v1/resolution/{candidate_id}/confirm`
- Accepts payload `{"canonical_entity_id": "..."}`.
- Transitions `resolution_status` to `RESOLVED` and assigns `resolved_to_id`.
- Appends the candidate's raw text to the canonical entity's `aliases` if missing.
- Records a `HUMAN_REVIEW_CONFIRM` event in the `EventAuditLog`.

## 6. Create Entity Action
`POST /api/v1/resolution/{candidate_id}/create-entity`
- Accepts payload `{"name": "..."}`.
- Transitions the candidate to `RESOLVED`.
- Creates a completely new `CanonicalEntity` initialized with the provided name.
- Assigns the new canonical ID to the candidate.
- Records a `HUMAN_REVIEW_CREATE` event in the `EventAuditLog`.

## 7. Reject Action
`POST /api/v1/resolution/{candidate_id}/reject`
- Transitions the candidate `resolution_status` to `REJECTED`.
- Purposely leaves `resolved_to_id` as `NULL`. The entity candidate remains as unlinked evidence attached to the source document.
- Records a `HUMAN_REVIEW_REJECT` event in the `EventAuditLog`.

## 8. RBAC and Authorization
All resolution endpoints enforce role-based access control (RBAC). Only authenticated users holding the `OFFICER`, `ADMIN`, or `EXECUTIVE` roles are permitted to execute these requests.

## 9. Audit Trail
Human decisions are tracked via `EventAuditLog`. Every destructive action records the `event_id` (the candidate ID), the action type (`HUMAN_REVIEW_CONFIRM`, `HUMAN_REVIEW_CREATE`, `HUMAN_REVIEW_REJECT`), the user identity, and the UTC timestamp.

## 10. PostgreSQL State Changes and Concurrency
Because API mutations validate the `candidate.resolution_status == 'REVIEW_REQUIRED'` immediately before applying state changes, concurrent reviews by two investigators are safely handled (the second request will yield an HTTP 400 failure due to the changed state).

## 11. Neo4j Synchronization
Any human decision resulting in a new or updated `CanonicalEntity` triggers `neo4j_intelligence.sync_canonical_entity()`. This preserves existing graph algorithms (Louvain/Leiden) and maintains graph-PostgreSQL state consistency.

## 12. Real-Data Validation Results
- The development database contained **84** `REVIEW_REQUIRED` entity candidates.
- The UI successfully surfaced these records, complete with dynamic `possible_matches`.
- M15.6 relies solely on genuine data and does not introduce mock candidates.
- The UI and API endpoints correctly enforce validation against actual canonical identities.

---

### Known Limitations
Currently, candidate context is displayed by file ID and page number. In future iterations, displaying the exact text snippet surrounding the extracted entity could further assist investigator context, leveraging the chunk vector database created in M15.4.
