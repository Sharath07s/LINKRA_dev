# M15.6 HUMAN REVIEW AND ENTITY RESOLUTION AUDIT

## 1. Current Resolution States
The `EntityCandidate` model defines the following resolution statuses:
- `UNRESOLVED`
- `REVIEW_REQUIRED`
- `RESOLVED`
- `REJECTED`
- `AUTO_MATCHED`

The backend already calculates `REVIEW_REQUIRED` based on matching confidence scores or explicit contradictions (like conflicting phone numbers), which veto an `AUTO_MATCHED` state.

## 2. Current Candidate Data Model
`EntityCandidate` includes:
- `id`: UUID of the candidate
- `ingestion_job_id`: Source reference
- `entity_type`: Target entity type (e.g., PERSON, ORGANIZATION)
- `raw_text`: Extracted text from source
- `normalized_value`: Normalized text
- `confidence`: Confidence of the extraction
- `source_page` / `source_row`: Precise location in the source
- `resolution_status`: Status of the candidate resolution
- `resolved_to_id`: UUID of the canonical entity if assigned
- `resolution_score`: Score generated during resolution
- `resolution_evidence`: Detailed evidence JSON from the resolution engine

## 3. Current Candidate APIs
The file `app/api/v1/resolution.py` has skeletal endpoints for human review:
- `GET /review-queue`: Fetches candidates with `resolution_status == 'REVIEW_REQUIRED'`. Currently, it only returns a single proposed match rather than a ranked list of `possible_matches`.
- `POST /{candidate_id}/approve`: Approves the merge (implicitly confirming the previously set `resolved_to_id`).
- `POST /{candidate_id}/create-entity`: Creates a new canonical entity from the candidate.

## 4. Current Canonical Entity APIs
Canonical entity creation already exists both within the ingestion pipeline (`resolve_candidate` -> `create_new_canonical`) and in the skeletal review queue API (`create_new_entity`).

## 5. Existing RBAC
`app/api/v1/resolution.py` defines access control via `Depends(deps.RoleChecker(["OFFICER", "ADMIN", "EXECUTIVE"]))`. All endpoints are appropriately restricted to authorized users.

## 6. Existing Neo4j Synchronization
Neo4j synchronization is currently invoked dynamically using `neo4j_intelligence.sync_canonical_entity` within the resolution API after merging or creating entities. This mechanism preserves downstream relationships and ensures Neo4j accurately reflects human decisions.

## 7. Exact Missing Functionality
The following items are missing or incomplete:
- **API `GET /review-queue`**: Needs to include multiple `possible_matches` correctly ranked by match score.
- **API `POST /{candidate_id}/confirm`**: Should accept `canonical_entity_id` explicitly instead of blindly approving `resolved_to_id`. Needs robust handling.
- **API `POST /{candidate_id}/create-entity`**: Should allow overriding the entity name.
- **API `POST /{candidate_id}/reject`**: Needs to be implemented to allow rejecting matches.
- **Concurrency control / Double Review**: We need to verify `resolution_status == 'REVIEW_REQUIRED'` strictly within a transaction or handle it correctly.
- **Frontend UI**: `app/resolution/page.tsx` must be rebuilt to dynamically fetch `possible_matches` from the backend and support Confirm/Reject/Create workflows with confirmations, adhering to the LINKRA M15.0 dark theme.

## 8. Proposed Minimal Implementation

### Backend Changes (`app/api/v1/resolution.py` & `app/nlp/resolution/engine.py`)
1. Implement a helper `get_possible_matches` in `app/nlp/resolution/engine.py` to reconstruct `ResolutionContext` and fetch/rank the top N canonical matches.
2. Update `GET /review-queue` to embed the ranked matches from `get_possible_matches` into `ResolutionReviewResponse.possible_matches`.
3. Update `POST /{candidate_id}/approve` -> `POST /{candidate_id}/confirm` to validate a provided `canonical_entity_id` payload.
4. Update `POST /{candidate_id}/create-entity` to validate a provided `name` payload.
5. Create `POST /{candidate_id}/reject` to set the `resolution_status` to `REJECTED`.
6. Use `EventAuditLog` (or create an explicit audit entry) to record the transition and reviewer.

### Frontend Changes (`src/app/resolution/page.tsx` & `src/services/resolution.service.ts`)
1. Extend `ResolutionReviewResponse` to include `possible_matches`.
2. Enhance `ResolutionService` to accept payloads for the updated APIs.
3. Replace the existing basic view in `page.tsx` with a rich UI listing all candidates and their ranked matches.
4. Add confirmation dialogs for all 3 critical actions (Confirm, Create, Reject).
5. Ensure empty, loading, and error states match the dark theme and existing design system.
