# LINKRA M1.4 Entity Resolution Verification & Hardening

## 1. Executive Summary
The M1.4 Entity Resolution system underwent a comprehensive verification and hardening audit to ensure it is robust enough to serve as the foundation for the upcoming M1.5 Relationship Extraction phase. Two critical defects were identified and fixed (Candidate Generation fuzzy matching limitation and API RBAC scope). The system enforces strict matching thresholds and correctly isolates ambiguous entities in the human-in-the-loop review queue without polluting the database with false positives.

## 2. Verification Scope
The audit spanned across the NLP resolution engine (`engine.py`, `candidate_generation.py`, `matching.py`), the Persistence layer (PostgreSQL CanonicalEntity), Graph synchronization (Neo4j intelligence.py), and the API layer (`resolution.py`), as well as test suites covering False Positive matrices.

## 3. Resolution Correctness
- **Verification Results**: `PASS`
- **Details**: The resolution engine distinguishes strictly between exact matches, ambiguous fuzzy matches, and new entities. It applies a `1.0` requirement for `PHONE` and `VEHICLE` to avoid erroneously merging slightly different identifiers (e.g., matching +919988776655 with +919988776656). For text-heavy entities like `PERSON` or `ORGANIZATION`, it uses a >= 0.95 and >= 0.75 thresholding logic to intelligently route identical or highly-similar candidates while pushing ambiguities to human review.

## 4. False-Positive / False-Merge Analysis
- **Verification Results**: `PASS` (After Fix)
- **Details**: 
  - Case A (Exact normalized entity): Correctly `AUTO_MATCHED`.
  - Case C (Similar but different, e.g. "Ravi Kumar" vs "Raju Kumar"): Fails threshold and correctly creates a new entity.
  - Case H (Ambiguous typo, e.g. "Ravi Kumar" vs "Ravi Kumarr"): Successfully routed to `REVIEW_REQUIRED`.
- *Issue Addressed*: The candidate generation initially filtered heavily in PostgreSQL (`CanonicalEntity.name == search_term`), which blocked `difflib` from scoring typographical variations. This was fixed by utilizing an `ilike(f"{prefix}%")` filter on the first 3 characters.

## 5. Provenance Verification
- **Verification Results**: `PASS`
- **Details**: `EntityCandidate` maintains full source references (`source_page`, `source_row`, offsets, `ingestion_job_id`) which inherently bridges the gap between the `CanonicalEntity` and the raw file evidence. The review queue seamlessly extracts this stringified source context to present to the user.

## 13. Issues Discovered

### Issue 1: Missing Fuzzy Candidate Generation
- **Severity**: High
- **Location**: `backend/app/nlp/resolution/candidate_generation.py`
- **Problem**: Candidate generation performed an exact strict DB lookup, preventing `difflib` from evaluating minor typos.
- **Impact**: Typos incorrectly spawned duplicate distinct entities (False Negatives).
- **Fix**: Adjusted SQLAlchemy filter to use `ilike` substring fetch for the first 3 characters, broadening the candidate pool safely without triggering O(N²) comparisons.
- **Regression Test**: Added `test_engine_fuzzy_typo` in `test_resolution_audit.py`.

### Issue 2: Weak RBAC on Review Queue
- **Severity**: Medium
- **Location**: `backend/app/api/v1/resolution.py`
- **Problem**: `GET /review-queue` permitted any authenticated user to view ambiguous records.
- **Impact**: Information leakage of unreviewed intelligence to basic roles.
- **Fix**: Applied `Depends(deps.RoleChecker(["OFFICER", "ADMIN", "EXECUTIVE"]))`.
- **Regression Test**: Verified by code inspection of route dependency.

## 16. Remaining Limitations
- Graph syncing operates synchronously which might stall HTTP ingestion loops if the Neo4j connection drops.
- `ilike` based substring matching works reasonably well but is less robust than a native PostgreSQL `pg_trgm` index for heavy text corpora. 

## 17. M1.5 Readiness
**Is M1.4 sufficiently verified and stable to become the foundation for Relationship Extraction / Knowledge Graph construction?**
**Yes.** The system guarantees that Canonical Entities form a stable, deduplicated truth layer. Evidence is strictly tracked, identities do not merge wildly out-of-bounds, and human intervention is properly staged. This reliable node architecture is perfectly primed to support edges/relationship extraction in M1.5.
