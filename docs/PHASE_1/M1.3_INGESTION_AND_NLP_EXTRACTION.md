# LINKRA — M1.3 Multi-Source Data Ingestion & NLP Extraction

## Overview
This document outlines the implementation of Milestone 1.3: Real Multi-Source Data Ingestion and NLP Extraction for the LINKRA platform. 

The primary goal of M1.3 is to transition away from placeholder ingestion and static datasets toward real, dynamic data processing while maintaining the established system architecture.

## Implementation Details

### 1. New Backend Models
Two new models were added to the system via Alembic migration (`a3f7c8d92e14`):
- **`IngestionJob`**: Tracks the lifecycle of an uploaded document (QUEUED → PROCESSING → PARSED → EXTRACTED → COMPLETED | FAILED).
- **`EntityCandidate`**: Stores extracted entity mentions along with full provenance data (confidence, source page, source row, start/end offsets, and extraction method).

### 2. File Parsers
Synchronous parsers were implemented to handle different file types natively:
- **PDF**: Uses `pypdf` to extract text while preserving page boundaries.
- **CSV**: Parses rows, validates headers, and extracts structured fields.
- **JSON**: Handles both objects and arrays, preserving record identity.
- **TXT**: Handles raw plain-text extraction with UTF-8 encoding support.

### 3. NLP Extraction Pipeline
A hybrid NLP extractor (`app/nlp/extractor.py`) was built to extract structured intelligence from raw text:
- **High-Precision Regex**: Extracts Indian phone numbers (`PHONE`) and vehicle registration plates (`VEHICLE`) first.
- **spaCy NER**: Uses `en_core_web_sm` to extract `PERSON`, `ORGANIZATION`, `LOCATION` (GPE/LOC), and `DATE`.
Overlap detection ensures that spaCy does not falsely classify a vehicle registration as an organization or a phone number as a date. 

### 4. API & Frontend Integration
- **Backend API**: A new router (`/api/v1/ingestion`) handles file uploads (`multipart/form-data`) and queries for jobs/entities.
- **Frontend Service**: Created `ingestion.service.ts` using `apiClient` to interface with the backend.
- **Frontend UI**: Built `/data-sources` page (client component) providing drag-and-drop file upload, job status tracking, and expandable details that group extracted entity candidates visually by type. 

## Architectural Constraints Adhered To
- **Preserved Existing Architecture**: Next.js, FastAPI, PostgreSQL, Neo4j, and existing schemas were completely untouched.
- **Synchronous Pipeline**: Adhered to the requirement of not introducing Celery/Redis for now.
- **Provenance Guaranteed**: Every entity candidate is tied directly to its exact location in the source document.
- **Truthful Intelligence**: No entity resolution or graph linking was artificially synthesized. This is strictly extraction.
