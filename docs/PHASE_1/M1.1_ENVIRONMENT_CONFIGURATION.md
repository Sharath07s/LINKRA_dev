# M1.1 — ENVIRONMENT & CONFIGURATION

## 1. Objective
Establish a clean, secure, documented, environment-driven configuration foundation for the existing ICA_AI application in preparation for the SIH26189 integration. This milestone focused strictly on environment management, hardcoded secrets removal, and centralized configuration, without changing business logic.

## 2. Pre-change Configuration Architecture
The existing application had a fragmented configuration architecture:
- JWT Secrets were hardcoded with insecure default values.
- PostgreSQL database credentials were inadvertently hardcoded in python source code (`vector_search.py`) and scripts (`ingest_fir_pdfs.py`).
- Docker Compose configuration provided hardcoded fallbacks that could leak into production.
- Frontend `.env.example` was missing, and the backend `.env.example` file was empty.
- CORS policies were overly permissive with a hardcoded wildcard origin (`allow_origins=["*"]`).
- `ALGORITHM` for JWT was statically defined inside the security package.

## 3. Configuration Problems Discovered
1. Hardcoded insecure database credentials in `backend/app/ai/rag/vector_search.py` and `backend/scripts/ingest_fir_pdfs.py`.
2. Hardcoded wildcard CORS domain policy in `backend/app/main.py`.
3. Insecure `SECRET_KEY = "your-secret-key-for-dev"` fallback in `backend/app/core/config.py`.
4. Empty or ineffective `.env.example` tracked in git.
5. Insecure fallback values in `docker-compose.yml`.

## 4. Environment Variable Contract
A clear environment variable contract was defined and published in the new `.env.example`. This includes:
- **Application**: `APP_ENV`, `APP_NAME`, `PROJECT_NAME`
- **Backend**: `API_V1_STR`, `CORS_ORIGINS`
- **Database**: `POSTGRES_SERVER`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`
- **Graph Database**: `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD`
- **Redis**: `REDIS_URL`
- **Security**: `SECRET_KEY`, `JWT_ALGORITHM`, `ACCESS_TOKEN_EXPIRE_MINUTES`
- **Frontend**: `NEXT_PUBLIC_API_URL`
- **AI**: `AI_PROVIDER` and corresponding `API_KEY`s.

## 6. Secrets Removed from Source
- Replaced `kcia_secret_password` and `kcia_user` with config-based injection in `vector_search.py` and `ingest_fir_pdfs.py`.
- Removed `your-secret-key-for-dev` from `config.py`. The `SECRET_KEY` is now strictly required.
- Removed insecure `neo4j_password` and `kcia_secret_password` fallback assignments in `docker-compose.yml`.

## 7. Backend Configuration Changes
- `config.py` was refactored using Pydantic's `BaseSettings` to enforce required variables (like `SECRET_KEY`).
- Added support for `CORS_ORIGINS` configurable string/list parsing to replace hardcoded strings.
- Exchanged scattered configurations for centralized imports from `app.core.config.settings`.

## 8. Frontend Configuration Changes
- Validated that `frontend/src/lib/api-client.ts` uses `NEXT_PUBLIC_API_URL` effectively.
- Confirmed there are still hardcoded fetch calls, which will be migrated in milestone M1.4 per instructions.
- Included `NEXT_PUBLIC_API_URL` in the centralized `.env.example` definition to aid frontend local configuration.

## 9. Database Configuration Changes
- PostgreSQL connection initialization in vector components correctly resolves from `settings.SQLALCHEMY_DATABASE_URI`.
- Insecure defaults in docker deployment files were replaced with mandatory environment bindings.

## 10. Neo4j Configuration Changes
- `neo4j.py` correctly consumes configuration from `settings.NEO4J_URI`.
- Cleared Neo4j connection string fallbacks from deployment code.

## 11. Redis Configuration Changes
- `REDIS_URL` configuration correctly resolves from the environment in `config.py`.

## 12. JWT Configuration Changes
- Stripped the `your-secret-key-for-dev` fallback.
- Abstracted the `ALGORITHM` from `security.py` constants into configurable `JWT_ALGORITHM`.
- Corrected dependent files (`deps.py`) to resolve standard settings.

## 13. CORS Configuration Changes
- Hardcoded `["*"]` block in `main.py` was switched to a dynamic parsing routine consuming the new `CORS_ORIGINS` setting to permit safe environment-specific setups.

## 14. Documentation Changes
- Updated `.gitignore` to allow commit tracking of `.env.example`.
- Created robust `.env.example` in root representing the exact contract.
- Updated `REQUIRED_ENV_VARIABLES.md` to reflect missing defaults and emphasize required security practices.

## 15. Verification Results
- **BACKEND IMPORTS:** PASS (Config injection verified functional; zero crashed modules)
- **BACKEND STARTUP:** PASS (Application loaded all dependencies)
- **SECRETS CHECK:** PASS (Manual grep found 0 hardcoded DB credentials or JWT keys)
- **FRONTEND CONFIG:** PASS (Valid logic identified in `api-client.ts`)

## 16. Blocked Tests
- No active blockers for local testing as mock/dummy config data in local `.env` satisfies all settings.
- E2E application functionality requires actual database provisioning which will proceed later.

## 17. Remaining Phase 0 Issues
- High severity missing RBAC constraints.
- Unauthenticated endpoints.
- Vulnerabilities to Cypher injection in dynamic searches.
- Hardcoded fetch requests in Frontend.

## 18. What M1.2 Will Address
- Milestone M1.2 will handle backend security hardening, removing wildcards entirely, mitigating Cypher injection flaws, enforcing RBAC rules across routes, and setting up rigorous rate-limiting constraints.

## 19. What was intentionally NOT changed
- No business logic, graph traversal routines, UI changes, predictive analytics algorithms, NLP models, LLM routing schemas, or database tables were changed.
- Hardcoded frontend APIs (`fetch("http://localhost:8000...")`) were deliberately preserved for Phase M1.4.
- In-memory event routing mechanics.
