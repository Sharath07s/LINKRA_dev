## 3. Canonical Entities
- **Person** (Implemented as `Suspect` / `Victim` tables)
- **Vehicle** (Implemented as `Vehicle` table)
- **Location** (Implemented as `District` / `PoliceStation` tables)
- **Case** (Implemented as `Crime` with `fir_number`)
- **Investigation** (Implemented as `Investigation` linked to `Crime`)
- **Evidence** (Implemented as `Evidence` linked to `Crime`)
- **Document** (Implemented partially as `DocumentChunk`)

## 4. Entity Identity Strategy
- **Current Strategy**: PostgreSQL UUIDs (`id`) are the canonical identifiers across the platform. Neo4j nodes store a matching `id` property referencing the PostgreSQL UUID.
- **Future Requirement**: 🔵 An Entity Resolution engine and Canonical Entity abstractions will be needed. Currently, entities are strictly separated by physical tables (e.g., `suspects`, `victims`). 

## 5. Case vs Investigation Distinction
- **Current Strategy**: 
  - `Case` is currently modeled as `Crime` (identified by `fir_number`).
  - `Investigation` is modeled as an active task assigned to an officer, linking back to a `Crime`. A single `Crime` can have multiple `Investigations`.
  - Evidence, Suspects, and Vehicles belong directly to the `Crime`, not the `Investigation`.

## 6. Document Contract
- **Current Strategy**: Documents are partially modeled as `DocumentChunk` with a raw string `source_id`.
- **Missing Contract**: 🔴 There is no overarching `Document` model tracking document metadata, source type, status, or original content references. 

## 7. Source & Provenance Contract
- **Missing Contract**: 🔴 There is no `Source` table or provenance tracking framework. Extracted entities and relationships currently cannot trace back to the exact source paragraph or document.

## 8. Evidence Contract
- **Current Strategy**: Evidence connects to `Crime`. Includes `evidence_type`, `file_name`, and `uploaded_by`.
- **Missing Contract**: 🔴 Evidence does not currently link to a specific `Document` or `Entity` extraction.

## 9. Relationship Contract
- **Current Strategy**: Modeled explicitly in PostgreSQL via join tables (`SuspectCrime`, `VictimCrime`, etc.). In Neo4j, relationships like `INVOLVED_IN`, `USED`, `ASSOCIATED_WITH` are present.
- **Missing Contract**: 🔴 Graph relationships currently lack confidence scores, temporal validity (`valid_from`/`valid_to`), and direct provenance links.

## 10. Location Contract
- **Current Strategy**: Geographically structured via `District` and `PoliceStation`. `Crime` contains explicit coordinates (`latitude`, `longitude`).
- **Missing Contract**: 🔴 Higher-level geography (e.g., `State`, `Country`) is absent.

## 11. Temporal Contract
- **Current Strategy**: Standard entity lifecycles use `created_at` / `updated_at`. Events use `occurrence_date`, `reported_date`, `started_at`, and `completed_at`.
- **Missing Contract**: 🔴 Graph edges (relationships) do not have explicit start/end timestamps.

## 12. Confidence Contract
- **Current Strategy**: Modeled only as a `risk_score` on `Suspects`.
- **Missing Contract**: 🔴 Extraction confidence and relationship confidence do not currently exist.

## 13. PostgreSQL ↔ Neo4j Contract
- **Current Strategy**: PostgreSQL is the primary truth store. Neo4j stores derived analytics copies (Nodes with corresponding Postgres `id` values). 
- **Missing Contract**: 🔴 Automated real-time synchronization pipelines between Postgres and Neo4j are not fully implemented.

## 14. API Contract
- **Status**: 🟢 **VERIFIED**. The FastAPI endpoints currently utilize Pydantic schemas that cleanly map to PostgreSQL SQLAlchemy models. 

## 15. Frontend Contract
- **Status**: 🟡 **PARTIAL**. The Next.js frontend has several standalone types (e.g. `IntelligenceCard` fields) that represent expected data (like `source`, `confidence`), which the backend APIs do not currently provide.

## 16. Ingestion Contract
- **Status**: 🔵 **FUTURE**. No unified pipeline contract for ingestion -> parsing -> NLP -> storage currently exists.

## 17. Intelligence-result Contract
- **Status**: 🔵 **FUTURE**. No centralized `IntelligenceResult` representation exists for bridging graph analytics outputs to evidence/UI components.

## 18. Copilot Contract
- **Status**: 🔵 **FUTURE**. Frontend Copilot interfaces exist, but backend agent orchestration mapping RAG, DB Tools, and Neo4j Tools to `Evidence` is incomplete.

## 20. Current Inconsistencies
- ⚠️ **Phone Numbers**: Phone nodes are queried in Neo4j but lack a corresponding canonical PostgreSQL table (`contact_number` exists merely as a string column on `Victim`).
- ⚠️ **Frontend Mock Fields**: Frontend components expect `confidence` and `provenance` metadata that the database currently cannot supply.

## 21. Missing Contracts (Summary)
- 🔴 Dedicated `Source` and `Document` tracking.
- 🔴 Entity Resolution identity management.
- 🔴 Provenance mapping (Entity -> Document -> Source).
- 🔴 Edge confidence and temporal bounds in Neo4j.

## 22. Recommended Future Changes
- Introduce `Source` and `Document` tables to properly ground RAG and entity extraction.
- Create an `EntityReference` table or unified identity layer for deduplication.
- Extend Neo4j edge properties to accept extraction `confidence` and `source_document_id`.
