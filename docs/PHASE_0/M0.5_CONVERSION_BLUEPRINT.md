# M0.5 — ICA → SIH26189 Conversion Blueprint

## 1. Executive Summary
This document serves as the master conversion blueprint for transforming the existing ICA_AI platform into a state-agnostic, AI-powered Criminal Intelligence & Network Investigation Platform that satisfies the requirements of Smart India Hackathon problem statement SIH26189. It consolidates findings from all Phase 0 milestones, identifies critical API mismatches, establishes architectural boundaries, and outlines the precise sequence of implementation phases.

## 2. Phase 0 Evidence Summary
The following read-only audits were completed to establish this blueprint:
- **M0.1 Project Freeze**: Baseline established at `v1.0-ica-baseline` (commit `1aeceed...`).
- **M0.2 Repository Inventory**: High-level mapping of Next.js, FastAPI, PostgreSQL, Neo4j, and Redis components.
- **M0.3 Backend Audit**: Deep analysis of ~90 FastAPI endpoints, identifying severe security flaws, missing RBAC enforcement, heuristic (non-ML) predictive engines, and heavy Karnataka/KSP coupling.
- **M0.4 Frontend Audit**: Analysis of the Next.js UI, revealing a polished visual layout but completely broken API integration layer (bypassing JWT auth) and missing ingestion/resolution interfaces.

## 3. Current ICA System Baseline
- **Frontend**: Next.js 16 (App Router), Tailwind CSS, Zustand. High-quality UI but relies heavily on mock data, hardcoded SVGs, and direct, unauthenticated `fetch()` calls.
- **Backend**: FastAPI with a modular router structure. Implements JWT auth but fails to enforce it broadly. Predictive endpoints use heuristics (Weighted Moving Averages, thresholding) rather than trained ML models.
- **Data Layer**: PostgreSQL (with pgvector for RAG), Neo4j (for criminal networks). Redis is configured but unused.
- **AI/ML**: A `FallbackManager` orchestrates multiple LLMs (Groq, Gemini, OpenAI, DeepSeek), but agentic reasoning is faked or hardcoded in places like the FIR extraction workflow.
- **Coupling**: Strongly tied to "Karnataka Crime Intelligence Assistant" (KCIA), hardcoded districts, and dummy FIR IDs.

## 4. SIH26189 Target State
The target system is a generalized, dynamic intelligence platform. Core requirements include:
- **Dynamic Multi-Source Ingestion**: PDFs, CSVs, etc., parsed dynamically.
- **NLP Entity Extraction & Resolution**: Automated extraction of entities, relationships, and a mechanism to merge duplicates with evidence provenance.
- **Knowledge Graph Analytics**: True network anomaly detection and link prediction.
- **AI Copilot**: An investigator assistant equipped with actual backend tools (SQL, Neo4j, Vector search) rather than static fallback prompts.
- **State-Agnostic**: Configurable geographic and jurisdictional bounds.

## 5. Backend ↔ Frontend Contract Mismatches

| Mismatch | Classification | Description & Evidence |
| -------- | -------------- | ---------------------- |
| **Authentication Headers** | **BLOCKING** | Frontend components use `fetch()` without `Authorization: Bearer <token>`, while backend endpoints require JWT via `get_current_active_user`. |
| **Hardcoded Entities** | **HIGH** | Frontend hardcodes IDs like `BLR-FIR-2026-0399` in `fir-workspace`, while backend expects dynamic lookup. |
| **Fake OTP Flow** | **HIGH** | Frontend `login/page.tsx` simulates a 1.2s handshake and accepts `"123456"` as OTP. Backend has no OTP verification logic. |
| **API URL Configuration** | **MEDIUM** | Frontend bypasses `NEXT_PUBLIC_API_URL` environment variables, hardcoding `http://localhost:8000/api/v1` in 30+ places. |
| **WebSocket Connectivity** | **MEDIUM** | Frontend expects real-time updates, but backend has two disjointed WS implementations (`ws.py` vs `realtime.py`) and EventBus doesn't scale. |

## 7. Assets to KEEP
- **Frontend Architecture**: The Next.js App Router setup, Tailwind CSS configuration, and `shadcn/ui` components provide a stellar foundation.
- **Dashboard Layouts**: `DashboardLayout.tsx` and navigational structures.
- **NetworkGraph Visualization**: The component for rendering nodes/edges is highly reusable.
- **Database Schema**: The existing PostgreSQL models (Users, Crimes, Suspects) and Neo4j node labels are generally adequate and should be preserved to avoid massive rewrite overhead.
- **JWT Generation Logic**: The token minting and hashing logic in `core/security.py` is solid.

## 8. Functionality to ADAPT
- **FIR Workspace**: Must be parameterized to load dynamic document IDs instead of hardcoded ones.
- **AI Assistant**: Needs to be connected to a real LangGraph tool-calling agent rather than a hardcoded prompt fallback chain.
- **Alert Engine**: Transition from synchronous, request-driven evaluation to a background task or cron job.

## 9. Architecture to REFACTOR
- **Frontend API Integration**: Create a centralized `axios` client with a request interceptor to attach the JWT token from `zustand` store.
- **Backend RBAC Enforcement**: Apply the `RoleChecker` dependency globally to all protected routes.
- **Security Flaws**: Remove wildcard CORS, secure all WebSocket endpoints, and eliminate the unauthenticated, arbitrary Cypher execution endpoint (`POST /neo4j/query`).
- **State-Agnostic Generalization**: Remove hardcoded "Karnataka", "KCIA", "KSP", and specific district names from LLM prompts, mock data, and UI text.

## 10. Functionality to REPLACE
- **Hardcoded SVG Maps**: Replace static SVGs in the dashboard with `maplibre-gl` implementations consuming dynamic GeoJSON.
- **Mock OTP Login**: Remove the simulated OTP delay and hardcoded "123456" validation. Implement standard JWT login or build a real MFA flow if required.

## 11. New Functionality to BUILD
- **Data Ingestion Hub**: A frontend UI and backend pipeline for uploading, parsing, and normalizing heterogeneous data (PDF, CSV).
- **Entity Resolution Engine**: Logic to calculate match scores and a UI for investigators to review/merge duplicated entities.
- **Evidence Provenance**: Traceability links ensuring every graph edge and AI statement links back to a specific document chunk.

## 13. SIH26189 Implementation Workstreams
- **Workstream A — Security & API Foundation**: Centralized Axios client, JWT interceptors, backend RBAC enforcement, removal of hardcoded secrets.
- **Workstream B — State-Agnostic Core**: De-branding KCIA/Karnataka, parameterizing workspaces.
- **Workstream C — Data Ingestion**: File upload UI, PDF/CSV parsers, normalization.
- **Workstream D — NLP & Entity Resolution**: Extraction pipeline, candidate matching, review UI.
- **Workstream E — Knowledge Graph**: Dynamic graph construction, centrality analytics, anomaly detection.
- **Workstream F — Investigator Copilot**: LangGraph tool orchestration, evidence provenance linking.
- **Workstream G — Mapping & Analytics**: MapLibre integration, replacing heuristic models with ML (time permitting).

## 15. Phase 1 Scope
**Phase 1 — Foundation & Tech Debt Eradication**
Phase 1 focuses solely on establishing a secure, connected, and generic baseline.
- **Deliverables**:
  1. Implement centralized `axios` client in frontend; replace all raw `fetch` calls.
  2. Enforce JWT and `RoleChecker` on all backend endpoints.
  3. Secure critical flaws (wildcard CORS, Cypher injection).
  4. Remove fake OTP from frontend login.
  5. De-brand "Karnataka/KCIA" into a generic "State Intelligence Platform".
  6. Parameterize `fir-workspace` to accept dynamic IDs.

## 16. Subsequent Phase Roadmap
- **Phase 2 — Data Ingestion & Processing**: Upload UI, document chunking, pgvector integration.
- **Phase 3 — Entity Intelligence**: NLP extraction, entity normalization, Entity Resolution UI.
- **Phase 4 — Knowledge Graph**: Neo4j dynamic population, graph analytics, visualization.
- **Phase 5 — AI Copilot & Evidence**: Tool-calling agents, exact provenance tracing.
- **Phase 6 — Analytics / Integration**: Dynamic Maps, ML integrations (XGBoost/LightGBM).
- **Phase 7 — Hardening**: Final QA, deployment readiness.

## 18. Protected Existing Assets
To prevent unnecessary AI-generated rewrites, the following must **NOT** be fundamentally changed without explicit justification:
1. **Next.js App Router & Tailwind CSS**: The visual aesthetic and routing structure are excellent.
2. **PostgreSQL Schema**: Existing models (`Crime`, `Suspect`, `DocumentChunk`) are adequate. Extend them rather than replace them.
3. **Neo4j Node Labels**: Current labels (`Suspect`, `Vehicle`, etc.) map well to the domain.
4. **JWT Minting**: `core/security.py` works well; just fix the default secret and enforce usage.
5. **LLM Provider Abstraction**: `FallbackManager` is a strong concept for resilience; keep it, but connect it to real LangGraph agents.
